## 1. Теория, которую нужно прочитать до начала

Oracle Database 23ai Documentation → *SQL Language Reference* и *Concepts*:

1. `CREATE USER`, `GRANT`, системные и объектные привилегии, `QUOTA ... ON tablespace`.
2. `CREATE TABLE`: inline- и out-of-line ограничения, **именованные** ограничения (`CONSTRAINT name ...`), `identity_clause`.
3. `CREATE INDEX`: функциональные индексы, `ORGANIZATION INDEX` (IOT).
4. *Concepts → Indexes and Index-Organized Tables*: как B-tree хранит `NULL`.
5. *Concepts → Data Concurrency and Consistency*: блокировки внешних ключей.
6. `COMMENT ON TABLE / COLUMN`.
7. `EXPLAIN PLAN`, пакет `DBMS_XPLAN`, `DBMS_STATS.GATHER_TABLE_STATS`.
8. Представления словаря данных: `USER_TABLES`, `USER_TAB_COLUMNS`, `USER_CONSTRAINTS`, `USER_CONS_COLUMNS`, `USER_INDEXES`, `USER_IND_COLUMNS`, `USER_IND_EXPRESSIONS`, `USER_TAB_IDENTITY_COLS`.

## 2. Структура в репозитории

```
db/
├── docker/                 # окружение (шаг 3.0)
├── migrations/             # V001__..., V002__... — применяются строго по порядку, только вперёд
├── seed/                   # справочники и демо-данные
├── tests/                  # тесты ограничений (шаг 3.8)
├── explain/                # запросы и сохранённые планы (шаг 3.10)
└── reset.sql               # полное удаление объектов схемы для локальной пересборки
```

Правило миграций: **применённый файл больше не редактируется**. Любое изменение — новый файл `V00N__...`. Объясните себе, почему (подсказка: что будет у коллеги, который уже применил старую версию?).

## 3. Шаги

### 3.0 Окружение
**Задача.** `docker-compose.yml` с образом `gvenzl/oracle-free` (тег 23-slim или 23): именованный volume для данных, healthcheck, пароли через `.env` (в репозиторий — только `.env.example`).

**Критерии приёмки**
- [ ] После `docker compose down` и повторного `up` данные на месте.
- [ ] `docker compose ps` показывает `healthy`.
- [ ] Подключаетесь клиентом (SQL Developer / расширение Oracle SQL Developer для VS Code / `sqlplus` в контейнере) к PDB `FREEPDB1`.

**Подумайте:** чем CDB отличается от PDB и почему схемы приложения создаются в PDB.

### 3.1 Пользователи схемы — `V001__users_and_privileges.sql`
**Задача.** Два пользователя:
- `SOUNDSHARE` — владелец объектов: может создавать таблицы, индексы, процедуры; имеет квоту в табличном пространстве.
- `SOUNDSHARE_APP` — пользователь приложения: **только** `CREATE SESSION` плюс объектные гранты (шаг 3.6). Никаких `CREATE TABLE`, `RESOURCE`, `DBA`.

**Критерии приёмки**
- [ ] Под `SOUNDSHARE_APP` команда `CREATE TABLE x (id NUMBER)` падает с ошибкой нехватки привилегий.
- [ ] Ни одному из пользователей не выдана роль `DBA`.

**Вопрос на понимание.** Приложение подключается как `SOUNDSHARE_APP`, а таблицы лежат в схеме `SOUNDSHARE`. Как писать `SELECT * FROM USERS` без префикса схемы? Найдите **два** способа и сравните их.

### 3.2 Таблицы — `V002__tables.sql`
**Задача.** Все 13 таблиц строго по разделу 4 модели данных.

**Требования**
- Порядок создания — топологический: родитель раньше потомка. **Сначала нарисуйте граф зависимостей на бумаге.** Одна таблица ссылается сама на себя: как это влияет на порядок?
- **Каждое** ограничение именуется по конвенции (`PK_`, `FK_`, `UQ_`, `CK_`). Безымянных `SYS_C00xxxx` быть не должно.
- `CHAR`-семантика у всех строковых колонок, где она указана в модели.
- Значения по умолчанию для времени — UTC-выражение из раздела 3 модели.

**Критерии приёмки**
- [ ] Запрос к `USER_CONSTRAINTS` по условию `CONSTRAINT_NAME LIKE 'SYS_C%'` возвращает только системные NOT NULL-ограничения. Почему они всё равно появятся и нормально ли это?
- [ ] Запрос к `USER_TAB_IDENTITY_COLS` показывает `GENERATION_TYPE = 'ALWAYS'` у 8 таблиц. Догадайтесь, у каких пяти таблиц identity **нет** и почему.
- [ ] Запрос к `USER_TAB_COLUMNS` подтверждает `CHAR_USED = 'C'` у строковых колонок.

### 3.3 Внешние ключи
Можно в том же файле, можно отдельным (`V003__foreign_keys.sql`).

**Задача.** Все FK со ссылочными действиями из раздела 4.14.

**Вопрос на понимание.** Зачем FK иногда выносят в отдельный файл после создания всех таблиц? Какую проблему это решает и как она связана с самоссылкой из шага 3.2?

### 3.4 Индексы — `V004__indexes.sql`
**Задача.**
1. Индексы на все FK-колонки, **не покрытые** ведущей колонкой существующего индекса (PK или UQ).
2. Семь функциональных индексов из раздела 6 модели, включая двухколоночный `UX_PT_POSITION`.
3. Решение по IOT для `TRACK_VOTES`, `SKIP_VOTES`, `TRACK_ARTISTS`: принять или отклонить, записать обоснование.

> ⚠ IOT задаётся только при создании таблицы. Если вы решите сделать IOT, это изменение в `V002`. Пока V002 нигде не применён, это допустимо, но запомните правило из раздела 2.

**Критерии приёмки**
- [ ] **Напишите сами** запрос к словарю данных, который находит FK-ограничения без поддерживающего индекса (колонки FK должны быть ведущими колонками какого-либо индекса). После шага 3.4 он возвращает 0 строк. Это классический вопрос на собеседовании DBA.
- [ ] `USER_IND_EXPRESSIONS` показывает выражения всех функциональных индексов.

### 3.5 Документация в словаре — `V005__comments.sql`
`COMMENT ON TABLE` и `COMMENT ON COLUMN` для всех таблиц и неочевидных колонок (`PINNED_AT`, `BANNED_UNTIL`, `EMPTY_SINCE`, `QUEUE_VERSION`, `POSITION`…). Источник формулировок — модель данных.

### 3.6 Гранты приложению — `V006__grants.sql`
- `SELECT, INSERT, UPDATE, DELETE` на прикладные таблицы.
- `AUDIT_LOGS` — только `SELECT, INSERT` (FR-AUD-05).
- `ROLES` — только `SELECT`.

**Критерий приёмки.**
- [ ] Под `SOUNDSHARE_APP` команды `UPDATE AUDIT_LOGS ...` и `DELETE FROM ROLES` падают с `ORA-01031`.

*(Процедура анонимизации с правами определителя (DM-13) — отдельная миграция позже. Подумайте пока, чем `AUTHID DEFINER` отличается от `AUTHID CURRENT_USER`.)*

### 3.7 Seed-данные — `db/seed/`
1. **`ROLES`**: `(1,'Admin')`, `(2,'User')`. Скрипт должен быть **идемпотентным**: повторный запуск не падает и не создаёт дублей. Подходящая конструкция Oracle уже упоминалась в ТЗ.
2. **Демо-набор**: 1 admin, ~10 пользователей, 3 комнаты (одна приватная), очереди, голоса.
   - Проблема: ID генерируются `ALWAYS`, вставить их явно нельзя. Как сослаться на только что созданного пользователя при вставке комнаты? Найдите способ без «магических» чисел.
3. **Объёмный набор** для шага 3.10: ~1 000 пользователей, ~50 000 позиций, ~500 000 голосов. Пишите генератор на SQL, а не тысячи `INSERT`. Ищите в документации генераторы строк (*row generator*).

**Критерии приёмки**
- [ ] Демо-данные проходят все ограничения: в комнате ровно один Owner, в каждой очереди не больше одной позиции `PLAYING` и т. д.
- [ ] Объёмный набор загружается меньше чем за минуту.

### 3.8 Тесты ограничений — `db/tests/constraints_test.sql`
**Самое полезное упражнение этапа.** На каждое ограничение — операция, которая **должна** упасть, и проверка, что упала она с **ожидаемым** кодом `ORA-xxxxx`. Если операция прошла, тест провален.

Оформите это как PL/SQL-блоки с перехватом исключения и проверкой `SQLCODE`. Каждый тест выводит `PASS` или `FAIL` с названием. Подумайте, как откатывать изменения теста, чтобы тесты не влияли друг на друга.

**Обязательные кейсы (≥ 18):**
1. Два пользователя `Vasya` и `VASYA`.
2. `EMAIL` — пустая строка `''`. Какой код ошибки и почему именно он?
3. Пользователь с несуществующим `ROLE_ID`.
4. `IS_ACTIVE = 2`.
5. Явная вставка значения в identity-колонку.
6. `VOTE_VALUE = 0` и `VOTE_VALUE = 2`.
7. Повторный голос того же пользователя за ту же позицию.
8. Две позиции `PLAYING` в одной очереди. А в **разных** очередях должно пройти!
9. Позиция `PLAYING` с `STARTED_AT IS NULL`.
10. Пользователь активен сразу в двух комнатах. А покинув первую, входит во вторую — должно пройти!
11. Два активных Owner в одной комнате.
12. Плейлист одновременно с `ROOM_ID` и `OWNER_ID`, а также ни с одним из них.
13. Вторая очередь у той же комнаты.
14. `INVITE_CODE = 'AB0CDE'` (содержит `0`) и `'abcdef'` (строчные).
15. Активный участник (`LEFT_AT IS NULL`) с `BANNED_UNTIL`.
16. Две позиции с `POSITION = 1` в одном личном плейлисте. И **обязательно** — две позиции с `POSITION = NULL` в одной очереди комнаты должны пройти (ловушка DM-12).
17. `TRACKS.DURATION_SEC = 0`.
18. Удаление исполнителя, у которого есть треки. А удаление трека должно каскадно удалить его `TRACK_ARTISTS`.
19. *(бонус)* Вставка `BANNED_UNTIL = TIMESTAMP '9999-12-31 23:59:59.9999999'`. Что произойдёт и почему (DM-11)?

**Критерий приёмки:** 100 % `PASS`, вывод приложен к PR.

### 3.9 Задача на проектирование: перестановка позиций
Пользователь перетаскивает трек с позиции 5 на позицию 2 в личном плейлисте из 10 треков. Позиции 2–4 сдвигаются на +1. Пройдёт ли наивный `UPDATE ... SET POSITION = POSITION + 1 WHERE POSITION BETWEEN 2 AND 4`, учитывая уникальный индекс `UX_PT_POSITION`?

**Исследование.** Ответ зависит от того, когда Oracle проверяет уникальность: после каждой строки или в конце оператора. И одинаково ли это для `UNIQUE`-**ограничения** и для **уникального индекса**, созданного через `CREATE UNIQUE INDEX`? Поставьте эксперимент на маленькой тестовой таблице для обоих вариантов, затем на `UX_PT_POSITION`. Результаты запишите. Это ценнее любого ответа из интернета.

Даже если одиночный `UPDATE` пройдёт, перестановка из приложения через EF Core выполняется **отдельными** `UPDATE` по строкам. Затем опишите в `docs/` минимум **два** способа решения со сравнением: сколько строк обновляется, атомарность, сложность. Направления для размышления: отложенные (deferrable) ограничения (и почему они не применимы к функциональному индексу), двухфазное обновление, позиции с промежутками. Код не нужен — нужен разбор вариантов.

### 3.10 Первый EXPLAIN PLAN — `db/explain/queue.sql`
**Задача.** Напишите запрос «очередь комнаты» по правилу FR-RT-03:
- только `QUEUED`;
- рейтинг — сумма голосов (позиция без голосов имеет рейтинг 0: **не потеряйте её** — какой JOIN нужен?);
- порядок: закреплённые → рейтинг → время добавления;
- номер в очереди через аналитическую функцию.

Затем:
1. Соберите статистику (`DBMS_STATS`) по объёмному набору.
2. `EXPLAIN PLAN FOR ...` и `DBMS_XPLAN.DISPLAY` — сохраните план.
3. Найдите в плане, какое обращение к таблице самое дорогое. Предложите индекс, создайте его в новой миграции, снимите план повторно.
4. Сравните **оценочный** план (`EXPLAIN PLAN`) с **фактическим** (`DBMS_XPLAN.DISPLAY_CURSOR` после выполнения запроса с хинтом `GATHER_PLAN_STATISTICS`): колонки `E-Rows` и `A-Rows`. Если они сильно расходятся, объясните почему.

**Критерий приёмки:** планы «до/после» и вывод в 3–5 предложениях в `db/explain/README.md`.

### 3.11 Пересборка с нуля
`reset.sql` удаляет все объекты схемы, после чего миграции V001…V00N и seed применяются заново **без единой ошибки**. Это и есть проверка, что ваши скрипты — источник истины.

## 5. Как распределить работу в команде

Цель «каждый понимает всё» и параллельная работа противоречат друг другу. Компромисс:
- **Шаги 3.0–3.2 каждый делает сам**, в своей локальной БД (ката). Затем сравниваете решения и сливаете лучшее в одну ветку `feature/db-schema`.
- **Шаги 3.3–3.11 делите**, но с обязательным перекрёстным ревью: автор тестов ограничений (3.8) ревьюит индексы (3.4) и наоборот. Ревьюер должен уметь объяснить чужой код на защите.
