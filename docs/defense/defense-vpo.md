# Ответы на вопросы

## Блок 1. Требования и виды тестирования (задания 1–2)

**1. Этапы жизненного цикла тестирования. С какого этапа начинается работа тестировщика? (§1.2)**
Цикл замкнут и повторяется на каждой итерации:
1. Общее планирование и анализ требований.
2. Уточнение критериев приёмки.
3. Уточнение стратегии тестирования.
4. Разработка тест-кейсов.
5. Выполнение тест-кейсов.
6. Фиксация найденных дефектов.
7. Анализ результатов тестирования.
8. Отчётность.

Работа тестировщика начинается с **первого этапа — анализа требований**, ещё до появления кода: чем позже найдена ошибка, тем дороже её исправление (§2.2). У меня дефекты DEF-001…008 найдены в ТЗ и модели данных до программирования.

**2. Что такое требование? Зачем нужны, кто источник и потребитель? (§2.1–2.3)**
- **Требование** — описание того, какие функции и с соблюдением каких условий приложение должно выполнять в процессе решения полезной для пользователя задачи.
- **Зачем нужны:** понять, что и при каких условиях должна делать система; оценить масштаб изменений и управлять ими; построить план, оценки, тесты; иметь критерий «дефект или так задумано».
- **Источник** — заказчик и представители пользователей. Требования выявляют интервью, анкетированием, семинарами, наблюдением, прототипированием, анализом документов, моделированием процессов.
- **Потребители** — аналитики, разработчики, тестировщики, менеджеры, заказчик.

У меня источником были ответы на вопросы о правилах (голос ±1, лимит 3 трека, порог −5), потребителями — код, тест-кейсы и автотесты.

**3. Уровни требований (§2.4)**
- **Бизнес-требования** — зачем нужен продукт (у меня BG-1…5).
- **Пользовательские требования** — что пользователь сможет делать: варианты использования, бизнес-правила, атрибуты качества (UR-01…08, UC-01…21, BR-VOTE/ROOM).
- **Продуктные требования** — функциональные, нефункциональные, ограничения, требования к интерфейсам и данным (FR, NFR, ТЗ §7, контракт API, модель данных).

**4. Функциональные и нефункциональные (§2.4)**
- **Функциональные** описывают поведение системы — что она делает. Пример: «позиция с рейтингом ≤ −5 получает статус AUTO_REMOVED».
- **Нефункциональные** описывают свойства — насколько хорошо: производительность, безопасность, надёжность, удобство. Пример: «p95 ≤ 200 мс при 100 RPS», «пароли хранятся как PBKDF2-хеш».

**5. Use case и актор**
- **Вариант использования** — сценарий взаимодействия актора с системой, дающий ему полезный результат (UC-08 «Проголосовать за трек»).
- **Актор** — внешняя роль, человек или система: гость, участник, модератор, администратор, YouTube Data API, таймер воспроизведения.

**6. Модульное, интеграционное, системное (§3.2, уровень детализации)**
- **Модульное** — отдельная часть в изоляции (`QueueRules`, `QueueService` с моками).
- **Интеграционное** — взаимодействие частей, каждая из которых проверена отдельно (репозиторий EF Core + Oracle).
- **Системное** — приложение целиком глазами пользователя (тест-кейсы через API и UI, Playwright).

**7. Белый, чёрный, серый ящик (§3.2, доступ к коду)**
- **Белый** — код доступен, тесты строятся по его структуре: ветви, условия.
- **Чёрный** — кода нет, тесты строятся по требованиям: вход → ожидаемый выход.
- **Серый** — доступ к части кода или внутреннего устройства, например знание схемы БД при тестировании через API.

**8. Позитивное и негативное (§3.2, §7.1). Поведение на негативный тест**
- **Позитивное** — корректные действия и данные по инструкции; если такой тест падает, это тревожный признак.
- **Негативное** — некорректные данные и операции; таких ситуаций в жизни больше.

На негативный тест система должна **не падать и не портить данные**: вернуть понятную ошибку и остаться в согласованном состоянии. У меня:
- неверные данные → 400 ProblemDetails с полем;
- нарушено бизнес-правило → 409;
- нет прав → 403;
- чужая приватная комната → 404;
- стека и SQL в ответе нет, ограничения БД (`CHECK`, `FK`, `UNIQUE`) страхуют на уровне данных.

**9. Метод моих тестов**
- Модульные — **белый ящик**: проверяют ветки `QueueRules` (граница −5, «строго больше половины»).
- Интеграционные — **серый**: знаю схему и проверяю строки в БД после вызова репозитория.
- Сценарные, Postman, Playwright — **чёрный**: только запрос и ответ по требованиям.

**10. Уровни представления, бизнес-логики и данных (§3.2, уровень архитектуры)**
- **Представление** — взаимодействие с внешним миром: UI, API, удобство, отклик, совместимость. У меня это Playwright, проверка вёрстки, Postman.
- **Бизнес-логика** — функции и бизнес-правила: юнит-тесты Domain/Application, сценарные тесты.
- **Данные** — хранение, целостность, правила в БД, производительность: `constraints_test.sql`, интеграционные тесты, замеры индексов.

**11. Регрессионное тестирование. Почему тест, нашедший дефект, оставляют (§3.2)**
Это проверка того, что в ранее работавшей функциональности не появились ошибки из-за изменений в коде или окружении. По Бруксу, 20–50 % исправлений порождают новую ошибку.

Тест, нашедший дефект, сначала подтверждает исправление (повторное тестирование), а затем сторожит, чтобы дефект не вернулся. У меня после DEF-014 добавлен `AdminEndpoint_RegularUser_DenialIsAudited`, после DEF-015 — проверка записи `Queue.AutoRemoved`.

**12. Что находит интеграционное тестирование, если модули уже проверены (§3.2)**
Проблемы «на стыках»: несовпадение типов и форматов, маппинг ORM ↔ СУБД, транзакции и блокировки, конфигурация, поведение внешних сервисов.

Пример — DEF-009: юнит-тесты проходили, а EF Core + провайдер Oracle падали на конвертере `bool → NUMBER(1)`. Другой пример — DEF-024: оптимистичная блокировка проявилась только при параллельной работе с настоящей БД.

**13. Сценарный, интеграционный и E2E-тест; пирамида тестирования**
- **Интеграционный** — стык двух-трёх компонентов.
- **Сценарный** — цепочка действий по бизнес-сценарию: добавить трек → голоса → `AUTO_REMOVED`. Сценарный подход описан в пособии со ссылкой на С. Канера.
- **E2E** — вся система так, как ей пользуются: браузер → клиент → API → БД, без заглушек (Playwright).

**Пирамида тестирования** (М. Кон): внизу много быстрых и дешёвых модульных тестов, выше меньше интеграционных, наверху немного медленных и хрупких E2E. У меня: 214 модульных, 60 интеграционных и сценарных, 12 UI.

## Блок 2. Тест-план, тест-кейсы, дефекты (задание 3)

**1. Что такое тест-план и его разделы (§6.2)**
Тест-план — документ, описывающий весь объём работ по тестированию: от описания объекта, стратегии, расписания и критериев начала и окончания до необходимого оборудования, знаний, оценки рисков и вариантов их разрешения.

Разделы (мой `test-plan.md`):
- цель;
- области, подвергаемые тестированию, и области, не подвергаемые тестированию (с обоснованием и ссылками на FR/NFR);
- тестовая стратегия и подходы;
- критерии;
- ресурсы;
- расписание;
- роли и ответственность;
- оценка рисков;
- документация;
- метрики.

**2. Что такое тестовая стратегия**
Это решение, *как* тестировать:
- уровни (модульное, интеграционное, системное);
- виды (функциональное, безопасность, производительность, совместимость);
- техники (классы эквивалентности, граничные значения, переходы состояний);
- инструменты (xUnit, Testcontainers, Postman, Playwright, NBomber);
- что автоматизируется, а что проверяется вручную.

**3. Критерии в тест-плане**
- **Приёмочные** — когда продукт можно считать готовым, например TSP ≥ 90 % на критическом пути и устранено 100 % критических и высоких дефектов.
- **Начала** — когда можно начинать: сборка проходит, окружение `healthy`, демо-данные загружены.
- **Приостановки** — когда тестирование бессмысленно продолжать: стоп-фактор S = Yes, окружение недоступно.
- **Возобновления** — когда можно продолжать: устранены блокирующие дефекты, метрика текущего устранения выше порога.
- **Завершения** — когда тестирование заканчивается: TE ≥ 95 %, все высокоприоритетные выполнены.

Нужны, чтобы решения принимались по числам, а не «на глаз».

**4. Метрики и формулы (§6.2)**
Метрика — числовая характеристика показателя качества процесса или продукта.

| Метрика | Формула | У меня |
|---|---|---|
| Успешное прохождение | TSP = T_Success / T_Total · 100 % (T_Total — выполненные) | 35 / 36 = 97,2 % |
| Выполнение | TE = T_Executed / T_Planned · 100 % | 36 / 38 = 94,7 % |
| Покрытие требований | R_C = R_Covered / R_Total · 100 % | M: 32 / 32 = 100 %; всего 50 / 94 тест-кейсами (95 % вместе с автотестами) |
| Устранение дефектов уровня Level | D^Level_FTP = D^Level_Closed / D^Level_Found · 100 % | высокие — 100 %, средние — 75 % |
| Стоп-фактор | S = Yes, если TE ≥ 25 % и TSP < 50 % | No |

**5. Чек-лист и его отличие от тест-кейса (§4.1)**
Чек-лист — набор идей тестов: что проверить, без детальных шагов и ожидаемых результатов. Тест-кейс — формализованная проверка с исходными данными, шагами и ожидаемым результатом. Чек-лист — быстрый и гибкий; тест-кейс — воспроизводимый и однозначный, его может выполнить другой человек.

**6. Тест-кейс и его атрибуты (§4.2–4.3)**
Тест-кейс — набор входных данных, условий выполнения и ожидаемых результатов, разработанный с целью проверки того или иного свойства или поведения программного средства.

Атрибуты (как в моих TC):
- идентификатор;
- приоритет;
- связанное требование;
- модуль и подмодуль;
- заглавие (суть);
- исходные данные;
- шаги;
- ожидаемые результаты.

**7. Свойства качественного тест-кейса (§4.5)**
- Правильный технический язык и точность.
- Баланс конкретности и общности, простоты и сложности.
- Проверяемость: однозначный ожидаемый результат. DEF-008 — у меня были «или»-ожидания, исправлено.
- Независимость от других тест-кейсов.
- Прослеживаемость к требованию.
- Отсутствие лишних действий.
- Неизбыточность по отношению к другим тест-кейсам.
- Демонстративность: показывает реальную проблему.
- Возможность повторного использования.

**8. Отчёт о дефекте и его цели (§5.2)**
Документ, описывающий ситуацию или последовательность действий, приведшую к некорректной работе объекта тестирования, с указанием причин и ожидаемого результата.

Цели:
- предоставить информацию о проблеме;
- указать степень опасности и срочность исправления;
- помочь разработчику устранить проблему.

**9. Как составить краткое описание (§5.3)**
Отвечает на вопросы **«Что? Где? При каких условиях?»** — коротко, без общих слов. Пример: «Параллельные голоса в одной комнате теряются с ответом 409» (DEF-024): что — голоса теряются; где — в комнате; при каких условиях — при параллельной отправке.

**10. Важность и срочность (§5.2)**
- **Важность (severity)** — степень ущерба для проекта: критическая, высокая, средняя, низкая.
- **Срочность (priority)** — как быстро нужно исправить: наивысшая, высокая, обычная, низкая.

Они независимы: опечатка в названии компании на главной странице — низкая важность и наивысшая срочность. Редкое падение в неиспользуемой функции — высокая важность и низкая срочность.

**11. Воспроизводимость, симптом, возможность обойти (§5.2)**
- **Воспроизводимость** — «всегда» или «иногда» (N из M попыток).
- **Симптом** — классификация проявления: косметический дефект, повреждение или потеря данных, проблема в документации, некорректная операция, проблема инсталляции, ошибка локализации, нереализованная функциональность, проблема масштабируемости, низкая производительность, крах системы, неожиданное поведение, недружественное поведение, расхождение с требованиями, предложение по улучшению.
- **Возможность обойти** — есть ли обходной путь. Влияет на срочность: у DEF-024 обход — повторить голос.

**12. Жизненный цикл отчёта о дефекте (§5.2)**
Основной путь: обнаружен (submitted) → назначен (assigned) → исправлен (fixed) → проверен (verified) → закрыт (closed).

Ответвления:
- открыт заново (reopened) — если проверка не прошла;
- рекомендован к отклонению → отклонён (declined) — если это не дефект;
- отложен (deferred) — если исправление переносится.

У меня DEF-019 и DEF-020 прошли путь «найден → исправлен → повторная проверка TC-19 и TC-26 → закрыт», а DEF-016 открыт с предложенным решением.

## Блок 3. Непрерывная интеграция (задание 4)

**1. Что такое CI и какие проблемы она решает**
Непрерывная интеграция — практика, при которой изменения часто сливаются в общую ветку, а каждое изменение автоматически собирается и проверяется тестами. Она решает такие проблемы:
- «у меня работает» — сборка идёт в чистом окружении;
- поздняя интеграция и большие конфликты слияния;
- регрессии, найденные через недели после появления;
- ручные, забытые или пропущенные проверки.

У меня — `.github/workflows/ci.yml`, запуск на каждый push и pull request в main.

**2. Continuous Delivery и Continuous Deployment**
- **Delivery (поставка)** — каждая сборка, прошедшая конвейер, *готова* к выпуску, но выпуск запускает человек.
- **Deployment (развёртывание)** — каждая прошедшая сборка выпускается в production автоматически, без ручного шага.

У меня реализована только CI; развёртывания нет, это учебный проект.

**3. Конвейер CI/CD и порядок стадий**
Стадии: получение кода → восстановление зависимостей → сборка → статический анализ → модульные тесты → интеграционные тесты → отчёты и quality gate → артефакты → (развёртывание на тестовый стенд → системные и E2E → production).

Порядок — «от быстрых и дешёвых к медленным и дорогим»: если не собралось или упал линтер, нет смысла поднимать Oracle в контейнере. Это принцип *fail fast*.

Мой конвейер:
1. checkout;
2. setup-dotnet (версия из `global.json`);
3. restore;
4. `build -c Release` (предупреждения = ошибки);
5. `dotnet format --verify-no-changes`;
6. модульные тесты Domain и Application;
7. интеграционные тесты (Testcontainers, Oracle в Docker на раннере);
8. ReportGenerator → сводка покрытия в Summary;
9. quality gate (покрытие строк ≥ 70 %);
10. upload-artifact (`.trx` и отчёт покрытия).

**4. Какие тесты на каких этапах; почему нагрузочные не на каждом коммите**
- На каждый коммит — модульные (секунды) и интеграционные (минуты): быстрые, детерминированные, ловят регрессии.
- UI-тесты (Playwright, три браузера) и Postman-коллекция — перед выпуском или по расписанию: долгие, им нужен запущенный стенд.
- Нагрузочные — отдельно, перед релизом или после изменений, влияющих на производительность. Причины:
  - они долгие (стресс у меня — около 5 минут);
  - требуют стабильного выделенного окружения — на общем раннере GitHub результаты не сравнимы между запусками;
  - сами создают нагрузку;
  - их результат — числа для анализа, а не pass/fail.

**5. Quality gate**
Набор формальных условий, при невыполнении которых конвейер останавливается и изменение не принимается. У меня:
- сборка без предупреждений;
- `dotnet format` без изменений;
- 100 % прохождения модульных и интеграционных тестов;
- покрытие строк ≥ 70 % (шаг awk по `Summary.txt`, при 86,9 % проходит).

**6. Артефакты и зачем сохранять отчёты**
Артефакты — файлы, которые создаёт конвейер: сборки, отчёты тестов (`.trx`), отчёт покрытия, логи, скриншоты и трассы UI-тестов. Отчёты сохраняют, чтобы:
- разобрать падение, не перезапуская сборку;
- доказать, что проверка была выполнена (аудит, защита);
- сравнивать динамику — покрытие и время между сборками.

**7. Требования к тестам и окружению в CI; flaky-тесты**
Тесты должны быть:
- независимыми и повторяемыми;
- изолированными по данным — у меня каждый интеграционный тест создаёт своих пользователей с уникальными именами;
- без зависимости от внешних сервисов — YouTube подменён WireMock;
- без «магических» пауз — ожидание по условию.

Окружение — воспроизводимое: версия SDK зафиксирована в `global.json`, БД в контейнере, секреты только из переменных окружения.

**Flaky-тест** — тест, который на одном и том же коде то проходит, то падает. Он подрывает доверие к CI: красная сборка перестаёт что-то значить. У меня было два таких теста:
- UI-поиск читал устаревший список результатов — исправлено ожиданием результата, содержащего текст запроса;
- Firefox загружал WASM дольше 5 с — таймаут ожиданий увеличен до 15 с.

Тесты WireMock тоже нестабильно работали через системный прокси — исправлено: `127.0.0.1` и `UseProxy=false`.

**8. Связь CI с регрессионным тестированием**
CI и есть автоматизированное регрессионное тестирование: при каждом изменении повторно прогоняется весь набор, который подтверждает, что ранее работавшая функциональность не сломалась. Каждое исправление дефекта у меня сопровождается регрессионным тестом (например, DEF-019, DEF-020, DEF-024), и CI не даст вернуть дефект незаметно.

## Блок 4. Совместимость, API, безопасность, автоматизация (задания 2–4)

**1. Тестирование совместимости и кроссбраузерность**
Тестирование совместимости проверяет работу продукта в разных окружениях: ОС, браузеры, разрешения экрана, версии платформы. Кроссбраузерное — частный случай: одинаковое поведение и отображение в разных браузерах и движках. У меня (`ui-compat.md`):
- Chromium (Chrome и Edge) и Gecko (Firefox);
- 7 страниц на нескольких ширинах — от 360 px (телефон, в Chrome и Edge с эмуляцией мобильного устройства) через 768 px (планшет) до 2560 px; масштаб 50 % и 200 % моделируется шириной окна;
- все 12 UI-тестов проходят во всех трёх браузерах.

**2. Вёрстка и реальные данные**
Вёрстку проверяют не только на «красивых» данных, но и на граничных: длинные названия без пробелов, пустые списки, полная очередь, длинные имена, узкий экран. Реальные данные ломают макет, который выглядел идеально на «Lorem ipsum».

У меня (`ui-compat.md`):
- название комнаты из 60 широких букв без пробелов — переносится по `overflow-wrap: anywhere`;
- пустая очередь и пустой плеер;
- полная очередь Rock & Metal Bar;
- таблицы администрирования с прокруткой внутри блока.

Критерий — нет горизонтальной прокрутки: `scrollWidth − clientWidth = 0`.

**3. Network и Console в DevTools**
- **Network** — все HTTP-запросы: метод, URL, статус, заголовки (`Authorization`, `Set-Cookie`), тело, время. Показывает, что UI действительно вызывает API, какой код вернулся и нет ли лишних запросов.
- **Console** — ошибки JavaScript и WASM, предупреждения и сообщения CSP. Чистая консоль — критерий прохождения у меня в UI-проверках.

**4. Что проверяется в API**
- коды состояния;
- структура и типы тела ответа (контракт);
- бизнес-логика;
- заголовки;
- валидация входных данных — обязательные поля, границы, форматы;
- аутентификация и авторизация;
- формат ошибок (Problem Details);
- идемпотентность и конкурентность;
- время ответа.

**5. Коды HTTP: 401 vs 403, 400 vs 404**
- **401 Unauthorized** — клиент не аутентифицирован: нет токена, или он просрочен или неверен.
- **403 Forbidden** — клиент известен, но прав нет: обычный пользователь открывает `/api/admin/*`, а Contributor закрепляет или пропускает трек.
- **400 Bad Request** — запрос некорректен: пустое название, неверный формат, нарушена валидация.
- **404 Not Found** — ресурс не существует. У меня для чужой приватной комнаты тоже 404, чтобы не раскрывать её существование.

Ещё: 409 — конфликт состояния, 429 — превышен лимит запросов, 503 — БД недоступна (DEF-022).

**6. Связывание запросов в Postman; переменные окружения**
Ответ одного запроса сохраняется в переменную в скрипте Tests (`pm.environment.set("accessToken", json.accessToken)`, `roomId`, `itemId`), а следующие запросы используют `{{accessToken}}` и `{{roomId}}`. Так строится сценарий «регистрация → вход → создать комнату → добавить трек → голосовать».

Переменные окружения (environment) отделяют данные стенда (`baseUrl`, учётные данные) от коллекции: одна коллекция запускается на разных стендах, а секреты не попадают в репозиторий. В Newman у меня отключён cookie jar (`disableCookies`), а cookie `rt` передаётся явно — иначе тест повторного использования refresh-токена проходил ложно.

**7. Тестирование безопасности и IDOR**
Тестирование безопасности проверяет защищённость данных и функций от несанкционированного доступа: аутентификация, авторизация, инъекции, XSS, утечки информации, заголовки, ограничения частоты запросов.

**IDOR** (Insecure Direct Object Reference) — доступ к чужому объекту подменой идентификатора в запросе. У меня (`security-checks.md`, TC-37, папка Postman `08 Security`):
- очередь чужой приватной комнаты → 404;
- голос за позицию другой комнаты через свою комнату → 404;
- перебор `roomId` → 404;
- роль `Admin` в теле регистрации (mass assignment) игнорируется.

**8. Почему ошибки не раскрывают стек, пути, SQL; зачем логирование**
Стек вызовов, пути к файлам, имена таблиц и текст SQL — это разведданные для атакующего: по ним видны технологии, структура БД и точки для инъекции. Клиент получает нейтральное сообщение и идентификатор трассировки (`traceId`), а подробности уходят в серверный лог. Пример — DEF-024: в ответе 409 раскрывался текст исключения EF Core, это исправлено.

Логирование нужно, чтобы:
- расследовать инциденты;
- связать ошибку пользователя с записью в логе по `traceId`;
- обнаруживать атаки;
- вести аудит действий — у меня это таблица `AUDIT_LOGS`.

**9. Выгоды и риски автоматизации; что автоматизировать (§3.2, §7)**
Выгоды:
- скорость и многократный прогон регрессии;
- точность без человеческого фактора;
- работа без участия человека (CI);
- то, что вручную невозможно: нагрузка, сотни комбинаций.

Риски и затраты:
- стоимость разработки и поддержки;
- хрупкость при изменении UI;
- ложное чувство безопасности;
- автотест проверяет только то, что запрограммировано, и не замечает «странного».

Автоматизировать стоит:
- часто повторяемое: регрессию, критический путь, smoke;
- стабильную функциональность;
- API и бизнес-логику;
- нагрузку;
- проверки на многих данных и в нескольких браузерах.

Не автоматизировать: юзабилити, разовые и исследовательские проверки, быстро меняющийся UI.

**10. Record & Playback; почему не ограничиваются Selenium IDE**
Record & Playback — запись действий пользователя в браузере и их воспроизведение (Selenium IDE, Playwright codegen). Это быстрый старт, но записанные скрипты:
- хрупкие — привязаны к абсолютным локаторам;
- без переиспользования — шаги дублируются;
- со слабыми проверками;
- без параметризации данных и с трудной поддержкой.

Поэтому на практике пишут код с фреймворком: у меня Playwright + xUnit, с ожиданиями по условию, `data-testid`-локаторами и Page Object.

**11. Page Object**
Шаблон, при котором каждая страница (или компонент) представлена классом. Класс инкапсулирует локаторы и действия (`RoomPage.SearchAndAddAsync(query)`, `RoomPage.VoteUpAsync(title)`, `AdminUsersPage.FilterBlockedAsync()`), а тест описывает только сценарий и проверки. При изменении вёрстки правится один класс, а не все тесты; тесты читаются как бизнес-сценарии. У меня — папка `tests/SoundShare.UiTests/Pages`.

## Блок 5. Производительность, статический анализ, трассируемость (задание 5)

**1. Тестирование производительности и его подвиды (классификация, §3.2)**
Исследование показателей скорости реакции приложения на внешние воздействия при нагрузке различного характера и интенсивности. Подвиды:
- **нагрузочное** — работа при ожидаемой нагрузке;
- **стрессовое** — поведение выше предельной нагрузки;
- **объёмное** — работа при большом объёме данных; у меня — 1 млн голосов и 500 тыс. записей журнала на этапе 7 МДиСУБД;
- **масштабируемости** — рост производительности при добавлении ресурсов;
- **конкурентное** — одновременный доступ;
- **на стабильность (надёжность)** — длительная работа под нагрузкой.

**2. Нагрузочное vs стрессовое**
- **Нагрузочное** — проверяет, что при *ожидаемой* нагрузке выполняются NFR. У меня: 100 RPS 60 с, p95 ≤ 40 мс при требовании ≤ 200 мс.
- **Стрессовое** — нагрузка выше расчётной: найти предел, характер отказа и способность к восстановлению. У меня: ступени 100 → 1000 RPS; деградация на 850–900 RPS без ошибок, запросы встают в очередь.

**3. Восстанавливаемость**
Способность системы вернуться к нормальной работе после пиковой нагрузки или сбоя без перезапуска и потери данных. У меня после прогона на 1000 RPS следующий прогон на 100 RPS сразу дал p95 22 мс, как в базовом. После остановки Oracle API отвечает 503 и сам восстанавливается при её запуске (TC-38, DEF-022).

**4. Профиль нагрузки**
Модель реального использования: какие операции, в какой пропорции, с какой интенсивностью и сколько пользователей. Мой профиль (`load-test-plan.md`):
- 70 % — чтение очереди;
- 20 % — голоса;
- 10 % — список комнат.

Модель открытая: NBomber `Inject` подаёт заданное число запросов в секунду независимо от времени ответа, как реальные пользователи.

**5. Метрики и почему перцентили**
Метрики:
- время ответа (p50, p95, p99, max);
- пропускная способность (RPS);
- процент ошибок;
- загрузка CPU и памяти сервера и БД.

Почему перцентили, а не среднее: среднее скрывает «хвост» — 95 быстрых ответов и 5 по 10 секунд дают «нормальное» среднее, хотя каждый двадцатый пользователь ждёт. p95 означает, что 95 % запросов уложились в это время, и это гарантия для большинства пользователей. Требование NFR-PERF-01 сформулировано через p95.

**6. Точка деградации и узкое место**
- **Точка деградации** — уровень нагрузки, после которого время ответа резко растёт или появляются ошибки. У меня — между 800 RPS (p95 голосов 169 мс) и 900 RPS (медиана 4 с).
- **Узкое место** — ресурс, который первым исчерпывается и ограничивает систему. У меня — CPU Oracle Free: около 2,5 ядра, лимит редакции. API загружен на 14 %, ошибок пула соединений нет.

Улучшения:
- кэш очереди по `QUEUE_VERSION`;
- индексы V009;
- денормализованный рейтинг.

**7. Недостоверность при генераторе и приложении на одной машине**
Генератор нагрузки сам потребляет CPU, память и сеть. Он конкурирует с приложением и БД за ресурсы, а сетевые задержки отсутствуют — запросы идут через loopback. Поэтому результаты:
- занижают время ответа (нет сети);
- могут занижать пропускную способность (генератор отбирает CPU);
- не переносятся на production.

Я указываю это ограничение в отчёте. Смягчение: на машине 28 ядер, а Oracle ограничена своим лимитом CPU, поэтому именно она, а не генератор, оказалась узким местом. Правильно — запускать генератор на отдельной машине в той же сети, что и пользователи.

**8. Статическое тестирование (классификация, §3.2)**
Тестирование без запуска кода: ревью требований и документации, инспекция кода, статический анализ инструментами. У меня:
- Roslyn-анализаторы `latest-recommended` с `TreatWarningsAsErrors`;
- `.editorconfig` и `dotnet format`;
- разовый строгий прогон `latest-all`.

`dotnet format` нашёл 18 нарушений IDE1006 (именование констант). В строгом профиле исправлены CA1062 (25 → 14), CA1032, CA1003, CA1307 — см. `lint-report.md`.

**9. Что линтер находит и чего не находит**
Находит:
- нарушения стиля и именования;
- потенциальные ошибки: null-аргументы, неосвобождённые ресурсы, сравнение строк без культуры;
- уязвимые шаблоны: SQL-конкатенация, слабая криптография;
- неиспользуемый код.

Не находит:
- ошибки бизнес-логики (неправильный лимит треков);
- несоответствие требованиям;
- ошибки конкурентности во время выполнения — DEF-024 нашёл только нагрузочный тест;
- проблемы производительности и интеграции с БД;
- ошибки UI и юзабилити.

Ложные срабатывания тоже бывают: CA1812 для классов, создаваемых DI.

**10. Матрица трассируемости**
Таблица, связывающая требования с тест-кейсами, автотестами и дефектами. Показывает:
- покрыто ли каждое требование;
- какие тесты затронет изменение требования;
- где концентрируются дефекты.

У меня — `traceability-matrix.md`, 94 требования.

**11. Покрытие требований vs покрытие кода**
- **Покрытие требований** — доля требований, для которых есть тесты: тест-кейсами 50 / 94 (53 %), автотестами 90 / 94 (95 %), приоритет M — 32 / 32. Отвечает на вопрос «проверили ли мы то, что нужно пользователю».
- **Покрытие кода** — доля строк или ветвей, выполненных тестами: 86,9 % строк и 72,3 % ветвей. Отвечает на вопрос «какой код не исполнялся тестами».

Одно не заменяет другое:
- 100 % покрытия кода не гарантирует, что реализованы все требования — нереализованная функция не даёт непокрытых строк;
- выполненная строка ещё не проверена утверждением.

**12. Требования без тестов и тесты без требований**
- **Требования без тестов** — риск: свойство может не работать, и никто не узнает. У меня 4: FR-STAT-01 и -02 (приоритет C, вне релиза), NFR-SCALE-01 и -02 (проверяются анализом, а не тестом).
- **Тесты без требований** — либо лишняя работа, либо пропущенное требование. У меня 5, и каждое — кандидат в новое требование: mass assignment → NFR-SEC, таймаут YouTube 5 с → NFR-REL, мобильная ширина → NFR-UX.

**13. Почему требования с наибольшим числом дефектов — зоны риска**
Принцип скопления дефектов (defect clustering) — один из принципов тестирования: дефекты распределены неравномерно и концентрируются в небольшом числе модулей — сложных, часто меняющихся, плохо специфицированных. Где уже нашли много дефектов, там с высокой вероятностью остались ещё. Туда направляют дополнительное тестирование и ревью.

У меня это:
- документация — 6 дефектов;
- FR-AUD — 5;
- BR-ROOM, FR-USR, BR-VOTE — по 4.

Голосование — ещё и место конкурентного DEF-024.
