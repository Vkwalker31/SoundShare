# Этап 7. Приложение, тестовые данные и обоснование индексов

## 1. Приложение и данные

- **Приложение** — REST API ASP.NET Core с клиентом Blazor WebAssembly ([README](../README.md), [руководство пользователя](08-user-manual.md)).
- **Демо-данные** для защиты — [`db/seed/demo.sql`](../db/seed/demo.sql): 13 пользователей, 3 комнаты, очереди с закреплённым, автоудаляемым и играющим треком, журнал.
- **Объёмные данные** для замеров — [`db/seed/volume/volume.sql`](../db/seed/volume/volume.sql), загрузка заняла 1 мин 54 с ([вывод](../db/explain/volume-load.txt)).

| Таблица | Строк | Как устроены данные |
|---|---:|---|
| USERS | 20 000 | Владельцы, участники онлайн и ушедшие участники |
| TRACKS / TRACK_ARTISTS | 50 000 / 50 000 | Уникальные ID видео |
| ROOMS / PLAYLISTS | 2 000 / 2 000 | Каждая пятая комната приватная |
| ROOM_MEMBERS | 32 000 | В каждой комнате 6 участников онлайн и 10 ушедших (история) |
| PLAYLIST_TRACKS | 320 000 | В каждой очереди 150 сыгранных или пропущенных позиций, 9 в очереди, 1 играет |
| TRACK_VOTES | 1 000 000 | По 3 голоса за сыгранные позиции и по 5 за активные |
| AUDIT_LOGS | 500 000 | 30 дней, 7 видов действий; половина — `Queue.Vote` |

Распределение повторяет реальную работу сервиса: история очереди растёт быстрее активной части, журнал — быстрее всех.

## 2. Методика

Скрипт [`db/explain/measure.sql`](../db/explain/measure.sql) для каждого запроса выводит `EXPLAIN PLAN` (`DBMS_XPLAN.DISPLAY`) и выполняет запрос 30 раз с переменными привязки. Метрики:

- **логические чтения** блоков на одно выполнение — из `V$MYSTAT`, статистика `session logical reads`; основная метрика, не зависящая от кэша и загрузки машины;
- **среднее время** выполнения, мс.

Порядок замера:

1. Схема V001–V008 (только индексы на внешних ключах и уникальные) + объёмные данные + `DBMS_STATS.GATHER_SCHEMA_STATS` → «до».
2. Миграция [`V009__performance_indexes.sql`](../db/migrations/V009__performance_indexes.sql) + сбор статистики → «после».

Для чтения `V$MYSTAT` локальному владельцу схемы выданы права `SELECT ON SYS.V_$MYSTAT, SYS.V_$STATNAME`. Полный вывод с планами: [до](../db/explain/result-before.txt), [после](../db/explain/result-after.txt).

## 3. Запросы

Это реальные запросы приложения (репозитории EF Core, `PlaybackWorker`) и запросы этапов 5–6.

| № | Запрос | Где используется | Частота |
|---|---|---|---|
| Q1 | Активные позиции очереди: `playlist_id = :p AND status IN ('QUEUED','PLAYING')` | `GET /queue`, каждое изменение очереди | Самый частый (70 % нагрузки) |
| Q2 | Участники онлайн: `room_id = :r AND left_at IS NULL` | Вход в комнату, голосование за пропуск | Частый |
| Q3 | Журнал по действию, 50 новых: `action = :a ORDER BY id DESC FETCH FIRST 50` | Журнал администратора (keyset) | Средний |
| Q4 | Журнал за последний час: `created_at >= now − 1 h` | Расследование инцидентов, запрос 6.4 | Средний |
| Q5 | Трек по началу названия: `UPPER(title) LIKE 'TRACK 4999%'` | Поиск по каталогу | Частый |
| Q6 | Активные треки пользователя: `playlist_id = :p AND added_by_id = :u AND status IN (…)` | Проверка лимита 3 трека при каждом добавлении | Частый |
| Q7 | Рейтинг позиции: `SUM(vote_value) WHERE playlist_track_id = :i` | Каждый голос | Самый частый на запись |
| Q8 | Закончившиеся треки: `status = 'PLAYING' AND started_at + duration <= now` | `PlaybackWorker`, раз в секунду | Постоянный фон |

## 4. Результаты

| № | План до | План после | Чтений до | Чтений после | Изменение | Время до → после, мс |
|---|---|---|---:|---:|---:|---|
| Q1 | `INDEX RANGE SCAN IX_PLAYLIST_TRACKS_PLAYLIST` (160 строк) + фильтр статуса по таблице | `INDEX RANGE SCAN IX_PLAYLIST_TRACKS_QUEUE` (10 строк) | 164 | 14 | **−91 %** | 0,33 → < 0,1 |
| Q2 | `INDEX RANGE SCAN PK_ROOM_MEMBERS` (16 строк) + фильтр `left_at` | `INDEX RANGE SCAN IX_ROOM_MEMBERS_ROOM_ACTIVE` (6 строк) | 18 | 8 | −56 % | < 0,1 |
| Q3 | `INDEX FULL SCAN DESCENDING PK_AUDIT_LOGS` + фильтр по действию | `INDEX RANGE SCAN DESCENDING IX_AUDIT_LOGS_ACTION_ID` (50 строк) | 12 | 11 | ≈ 0 | 0,33 → < 0,1 |
| Q4 | `TABLE ACCESS FULL AUDIT_LOGS` (500 000 строк) | `INDEX RANGE SCAN IX_AUDIT_LOGS_CREATED` (661 строка) | 5 991 | 666 | **−89 %** | 22,3 → 0,7 |
| Q5 | `TABLE ACCESS FULL TRACKS` | `INDEX RANGE SCAN IX_TRACKS_TITLE_UPPER` | 489 | 4 | **−99 %** | 8,3 → < 0,1 |
| Q6 | `BITMAP AND` двух индексов (`…_ADDED_BY`, `…_PLAYLIST`) | `INDEX RANGE SCAN IX_PLAYLIST_TRACKS_QUEUE` | 39 | 8 | −79 % | 0,33 → < 0,1 |
| Q7 | `INDEX RANGE SCAN PK_TRACK_VOTES` | без изменений | 4 | 4 | — | < 0,1 |
| Q8 | `TABLE ACCESS FULL PLAYLIST_TRACKS` (320 000) + `HASH JOIN` | `INDEX RANGE SCAN IX_PLAYLIST_TRACKS_STATUS` (2 000) + `HASH JOIN` | 2 949 | 517 | **−82 %** | 14,3 → 4,0 |

Время ниже 0,1 мс округляется `DBMS_UTILITY.GET_TIME` (шаг 10 мс на 30 выполнений) до нуля; поэтому основная метрика — логические чтения.

## 5. Обоснование каждого индекса

| Индекс | Запросы | Почему такой |
|---|---|---|
| `IX_PLAYLIST_TRACKS_QUEUE (playlist_id, status, added_by_id)` | Q1, Q6 | Очередь хранит историю, и с ростом комнаты 94 % позиций — сыгранные. Индекс по `playlist_id` выбирал всю историю и отбрасывал её по таблице. Составной индекс сразу сужает выборку до активных позиций; третий столбец превращает проверку лимита в чтение одного индекса. **Заменяет** индекс внешнего ключа `IX_PLAYLIST_TRACKS_PLAYLIST` (тот же ведущий столбец), поэтому старый удалён — меньше затрат на вставку |
| `IX_PLAYLIST_TRACKS_STATUS (status, started_at)` | Q8 | Ежесекундный фоновый запрос читал всю таблицу ради 2 000 строк `PLAYING` (0,6 %). Низкая кардинальность статуса здесь не мешает: нужное значение редкое, и после сбора статистики с гистограммой оптимизатор это учитывает |
| `IX_ROOM_MEMBERS_ROOM_ACTIVE (room_id, left_at)` | Q2 | Отбирает только участников онлайн без чтения строк ушедших; `NULL` в `left_at` хранится в составном индексе, потому что первый столбец не пустой |
| `IX_AUDIT_LOGS_ACTION_ID (action, id)` | Q3 | Журнал — самая быстрорастущая таблица. На частых действиях обход первичного ключа по убыванию тоже быстр, но для редких действий он прочитал бы почти весь журнал. Составной индекс гарантирует 50 строк за `FETCH FIRST` при любом действии и поддерживает keyset-пагинацию (`id < :cursor`) |
| `IX_AUDIT_LOGS_CREATED (created_at)` | Q4, 6.2, 6.4 | Фильтры по периоду иначе читают весь журнал: время растёт линейно с размером таблицы |
| `IX_TRACKS_TITLE_UPPER (UPPER(title))` | Q5 | Функциональный индекс под регистронезависимый поиск по началу названия. Запрос «содержит» (`LIKE '%…%'`) B-дерево не ускоряет — для него предлагается Oracle Text (`CONTEXT`-индекс) или ограничение поиска префиксом |

## 6. Индексы, которые не создавались

| Кандидат | Почему не нужен |
|---|---|
| `TRACK_VOTES (playlist_track_id)` | Первичный ключ `(playlist_track_id, user_id)` уже начинается с этого столбца — Q7 читает 4 блока |
| `PLAYLIST_TRACKS (status)` отдельно | Покрыт `IX_PLAYLIST_TRACKS_STATUS` |
| `AUDIT_LOGS (user_id, id)` | Фильтр по пользователю обслуживается индексом внешнего ключа `IX_AUDIT_LOGS_USER`; добавлять составной индекс на таблицу с самой интенсивной вставкой без измеренной пользы — лишняя нагрузка на запись |
| Битовые (bitmap) индексы на статусы | Таблицы с частыми конкурентными изменениями (голоса, очередь); bitmap-индексы блокируют диапазоны строк при изменении |
| Денормализованный рейтинг вместо `SUM` | Отвергнут в модели данных (3НФ); Q7 и так стоит 4 чтения |

## 7. Связь с нагрузочным тестированием

Нагрузочный тест ([отчёт](testing/load-test-report.md)) показал, что узкое место при 850–900 RPS — CPU базы данных (лимит Oracle Free). Индексы V009 уменьшают работу БД на самые частые запросы очереди в 5–10 раз и фоновый запрос автоперехода — в 6 раз, то есть сдвигают точку деградации. Цена — шесть новых индексов (один индекс внешнего ключа удалён как поглощённый составным) и соответствующие затраты на вставку и обновление; на `PLAYLIST_TRACKS` число индексов выросло только на один.

## 8. Как повторить

```bash
# схема без V009, объёмные данные
sqlplus soundshare@//localhost:1521/FREEPDB1 @reset.sql
# V001–V008 по одной, затем:
sqlplus soundshare@//localhost:1521/FREEPDB1 @seed/volume/volume.sql
sqlplus soundshare@//localhost:1521/FREEPDB1 @explain/measure.sql      # до
sqlplus soundshare@//localhost:1521/FREEPDB1 @migrations/V009__performance_indexes.sql
sqlplus soundshare@//localhost:1521/FREEPDB1 @explain/measure.sql      # после
```
