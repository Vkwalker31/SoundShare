# План тестирования SoundShare

| | |
|---|---|
| **Версия** | 1.0 |
| **Объект** | SoundShare: Web API, SignalR, клиент Blazor WebAssembly, схема Oracle |
| **Основание** | [Техническое задание](../01-technical-specification.md) v1.2, [матрица верификации](../requirements/verification-matrix.md) |

## 1. Цель тестирования

Подтвердить, что SoundShare выполняет функциональные требования с приоритетом M и нефункциональные требования безопасности, целостности данных и производительности; найти и устранить дефекты до защиты; получить измеримые показатели качества: процент прохождения, покрытие требований, покрытие кода.

## 2. Области тестирования

### 2.1 Тестируется

| Область | Требования | Почему важно |
|---|---|---|
| Аутентификация и сессии | FR-AUTH-01…11 | Вход в систему, защита учётных записей |
| Управление пользователями | FR-USR-01…05, BR-ACC-01 | Обязательная функция; права администратора |
| Комнаты и участники | FR-ROOM-01…03, BR-ROOM-01…08 | Основной сценарий, правила доступа и бана |
| Очередь и голосование | FR-RT-03, FR-RT-07, BR-VOTE-01…09 | Ядро продукта, конкурентный доступ |
| Real-time и воспроизведение | FR-RT-01, 02, 04…06, 08, BR-TRK-05, BR-TRK-06 | Ценность «живой» очереди и синхронного звука |
| Журнал аудита | FR-AUD-01…08 | Обязательная функция; требования безопасности |
| Каталог и интеграция с YouTube | FR-CAT-01, FR-INT-01, FR-INT-02, BR-TRK-01…04 | Внешняя зависимость с квотой |
| Статистика | FR-STAT-01 | Аналитические запросы |
| Безопасность | NFR-SEC-01…08 | IDOR, утечки данных в ошибках, права БД |
| Целостность и транзакции | NFR-TX-01…04, схема БД | Ограничения и атомарность |
| Производительность | NFR-PERF-01…04, FR-RT-01 | Целевые времена ответа и доставки событий |
| Надёжность | NFR-REL-01…03, NFR-SCALE-01 | Переподключение, перезапуск, проверки здоровья |
| Клиент: вёрстка и совместимость | Задание 4 | Отображение в 3 браузерах и на мобильной ширине |

### 2.2 Не тестируется

| Область | Требования | Обоснование |
|---|---|---|
| Масштабирование через Redis backplane | FR-RT-09 | Приоритет C, требуется несколько экземпляров API и Redis — вне учебного стенда |
| Секционирование журнала и хранение 90 дней | FR-AUD-09 | Приоритет C; секционирование недоступно в Oracle Free |
| Топ пользователей по комнатам | FR-STAT-02 | Приоритет C, функция не реализуется в текущей версии |
| HSTS и сертификаты в production | NFR-SEC-01 (часть) | Production-развёртывания нет; на стенде проверяется только перенаправление на HTTPS |
| Плеер и стриминг YouTube | BR-TRK-01 | Сторонний компонент; проверяется только встраивание и управление позицией |
| Трассировка OpenTelemetry | NFR-OBS-02 | Нет коллектора на стенде; проверяется демонстрацией при наличии времени |
| Мобильные приложения, платежи, чат | Вне границ системы (ТЗ §2.4) | Функции не входят в систему |

## 3. Стратегия

### 3.1 Уровни тестирования

| Уровень | Что проверяется | Инструменты | Задание ВПО | Веха |
|---|---|---|---|---|
| Модульное | Доменные правила (переходы статусов, пороги голосов, лимиты), валидаторы, обработчики команд с подменой зависимостей | xUnit, NSubstitute, Shouldly | 2 | M2 |
| Интеграционное | Работа с Oracle (ограничения, `MERGE`, транзакции), внешний API через заглушку | Testcontainers (`gvenzl/oracle-free`), WireMock.Net, `constraints_test.sql` | 2 | M0–M2 |
| Сценарное | Цепочки вызовов API, переводящие позицию очереди по состояниям | `WebApplicationFactory`, xUnit | 2 | M2 |
| API | Все эндпоинты вариантов использования: позитивные, негативные, связанные запросы | Postman, Newman (отчёт htmlextra) | 4 | M2 |
| Системное ручное | Тест-кейсы TC-01…TC-38 на развёрнутой системе | Браузер, Postman, SQL*Plus | 3 | M3 |
| UI | Вёрстка, адаптивность, интерактивность, кроссбраузерность; автотесты сценариев | DevTools; Playwright for .NET (Page Object) | 4 | M3 |
| Безопасность | Прямой доступ без авторизации, IDOR, утечки в ошибках, журналирование | Postman, ручные проверки | 4 | M2–M3 |
| Нагрузочное | Базовый, нагрузочный, стрессовый прогоны | NBomber | 5 | M4 |
| Статический анализ | Нарушения правил кода | .NET analyzers, SonarAnalyzer.CSharp, `dotnet format` | 5 | M2–M4 |

### 3.2 Виды тестирования

Функциональное (позитивное и негативное), граничных значений (лимиты 3 трека, 100 участников, порог −5, ровно 50 % голосов), конкурентного доступа, безопасности, совместимости, производительности, регрессионное (автотесты в CI на каждый коммит), дымовое (смоук: TC-01, TC-05, TC-16, TC-21, TC-23 перед каждым циклом).

### 3.3 Тестовое окружение

| Компонент | Конфигурация |
|---|---|
| БД | Oracle 23ai Free в Docker; проверка совместимости — Oracle XE 21 (`--profile compat`) |
| Данные | Миграции V001–V006 + [демо-набор](../../db/seed/demo.sql); для нагрузочных тестов — объёмный набор |
| Приложение | Docker Compose: API + клиент + БД |
| Браузеры | Chrome, Firefox, Edge последних версий; мобильная эмуляция в DevTools; WebKit через Playwright |

### 3.4 Риски

| Риск | Влияние | Мера |
|---|---|---|
| Исчерпание квоты YouTube API | Блокирует TC-35 | Заглушка WireMock; локальный каталог |
| Поздняя готовность клиента | Сдвигаются UI-проверки | API и ручные тесты выполняются через Postman |
| Различия Oracle 19c/21c/23ai | Ошибки на лабораторном сервере | Прогон миграций и тестов ограничений на XE 21 |

## 4. Критерии

| Критерий | Условие |
|---|---|
| **Начала** | Сборка проходит; `constraints_test.sql` — 100 % PASS; окружение `healthy`; демо-данные загружены; тест-кейсы прошли ревью |
| **Приостановки** | Дефект критической важности блокирует ≥ 20 % запланированных тест-кейсов; или смоук-тест пройден менее чем на 80 %; или окружение недоступно дольше 4 часов |
| **Возобновления** | Блокирующий дефект исправлен и перепроверен; смоук-тест — 100 % |
| **Завершения** | Выполнено 100 % тест-кейсов высокого приоритета и ≥ 95 % всех; процент прохождения ≥ 90 %; покрытие M-требований тест-кейсами 100 %; устранено 100 % критических и значительных дефектов; покрытие кода автотестами ≥ 70 % |
| **Приёмки** | Сценарии UC-01…UC-21 проходят на демо-данных; нет открытых критических и значительных дефектов; NFR-PERF-01 выполнено под нагрузкой (p95 ≤ 200 мс при 100 RPS) |

## 5. Метрики

| Метрика | Формула | Целевое значение |
|---|---|---|
| Процент успешного прохождения тест-кейсов | `P = N_пройдено / N_выполнено × 100 %` | ≥ 90 % |
| Процент выполнения тест-кейсов | `E = N_выполнено / N_запланировано × 100 %` | 100 % для высокого приоритета, ≥ 95 % всего |
| Покрытие требований тест-кейсами | `C = R_покрыто / R_всего × 100 %`, где `R_покрыто` — требования, связанные хотя бы с одним тест-кейсом | 100 % для FR приоритета M |
| Процент устранения дефектов по важности | `F_i = D_устранено,i / D_найдено,i × 100 %` для каждой степени важности `i` | 100 % для критических и значительных, ≥ 80 % для умеренных |
| Покрытие кода | Строки, выполненные автотестами, / все строки (без миграций, конфигурации, сгенерированного кода) × 100 % | ≥ 70 % |

Шкала важности дефектов: **критическая** (система или ключевой сценарий не работает, потеря данных, уязвимость), **значительная** (функция работает неверно, обхода нет), **умеренная** (есть обходной путь), **незначительная** (косметика).

Текущие значения на этапе подготовки: запланировано 38 тест-кейсов; покрытие FR приоритета M — 32 из 32 (100 %); выполнение — 0 % (приложение в разработке).
