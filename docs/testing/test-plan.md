## 1. Цель

SoundShare — сервис совместного прослушивания с очередью, формируемой голосованием в реальном времени. Первостепенное внимание при тестировании уделяется:
- корректности очереди: порядок, голоса, лимиты, автоудаление, пропуск;
- синхронности: изменения и воспроизведение одинаковы у всех участников комнаты;
- безопасности: аутентификация, права в комнате, отсутствие доступа к чужим данным;
- целостности данных при одновременных действиях пользователей.

## 4. Тестовая стратегия и подходы

### 4.1 Уровни тестирования

| Уровень | Что проверяется | Инструменты | Задание ВПО |
|---|---|---|---|
| Модульное | Доменные правила (переходы статусов, пороги, лимиты), валидаторы, обработчики команд с подменой зависимостей | xUnit, NSubstitute, Shouldly | 2 |
| Интеграционное | Работа с Oracle (ограничения, `MERGE`, транзакции); внешний API через заглушку | Testcontainers (`gvenzl/oracle-free`), WireMock.Net, `db/tests/constraints_test.sql` | 2 |
| Сценарное | Цепочки вызовов API, переводящие позицию очереди по состояниям | `WebApplicationFactory`, xUnit | 2 |
| API | Все эндпоинты вариантов использования: позитивные, негативные, связанные запросы | Postman, Newman (отчёт htmlextra) | 4 |

| Нагрузочное | Базовый, нагрузочный, стрессовый прогоны | NBomber | 5 |

### 4.2 Подходы и виды тестирования

- **Дымовое тестирование** (TC-01, TC-05, TC-16, TC-21, TC-23) — перед каждым циклом; без его прохождения на 100 % тестирование критического пути не начинается.
- **Тестирование критического пути** — тест-кейсы высокого приоритета; затем расширенное тестирование (средний и низкий приоритет).
- **Позитивное и негативное** тестирование каждой функции (см. [чек-лист](checklist.md)).
- **Классы эквивалентности и граничные значения**: лимит 3 трека (3 и 4), 100 участников (100 и 101), порог автоудаления (−4 и −5), голосование за пропуск (ровно 50 % и больше 50 %), длина имени (2, 3, 32, 33 символа).
- **Тестирование конкурентного доступа**: одновременные голоса, автопереход, вход в комнату.
- **Регрессионное** — автотесты в CI на каждый коммит; повторное выполнение тест-кейсов по исправленным дефектам.
- **Тестирование безопасности**: доступ без авторизации, IDOR, утечки в сообщениях об ошибках.

## 5. Критерии

Метрики, на которые ссылаются критерии, определены в разделе 11.

| Критерий | Условие |
|---|---|
| **Приёмочные** | Успешное прохождение 100 % тест-кейсов дымового теста и не менее 90 % тест-кейсов критического пути (метрика `TSP`); устранено 100 % дефектов критической и высокой важности (метрика «Общее устранение дефектов», финальная фаза); покрытие функциональных требований тест-кейсами — 100 % для приоритета M и не менее 90 % в целом (метрика `RC`); выполнено NFR-PERF-01 (p95 ≤ 200 мс при 100 RPS) |
| **Начала тестирования** | Выход билда: сборка проходит, автотесты зелёные; `constraints_test.sql` — 100 % PASS; окружение в состоянии `healthy`; загружены демо-данные |
| **Приостановки тестирования** | Стоп-фактор `S = Yes` (выполнено не менее 25 % запланированных тест-кейсов, а успешно пройдено менее 50 % из них); или дымовой тест пройден не на 100 % — к критическому пути не переходим; или окружение недоступно дольше 4 часов |
| **Возобновления тестирования** | Текущее устранение дефектов не ниже порогов таблицы 11.3 для текущей фазы; дымовой тест — 100 % |
| **Завершения тестирования** | Выполнение тест-кейсов `TE` ≥ 95 % (минимум 80 %), для тест-кейсов высокого приоритета — 100 % |

## 11. Метрики

### 11.1 Успешное прохождение тест-кейсов

$$TSP = \frac{T_{Success}}{T_{Total}} \cdot 100\%$$

где `TSP` — процентный показатель успешного прохождения тест-кейсов; `T_Success` — количество успешно выполненных тест-кейсов; `T_Total` — общее количество выполненных тест-кейсов.

Минимальные границы: начальная фаза — 10 %, основная — 40 %, финальная — 80 %.

### 11.2 Общее устранение дефектов

$$D^{Level}_{FTP} = \frac{D^{Level}_{Closed}}{D^{Level}_{Found}} \cdot 100\%$$

где `D^Level_FTP` — процентный показатель устранения дефектов уровня важности `Level` за время существования проекта; `D^Level_Closed` — количество устранённых дефектов этого уровня; `D^Level_Found` — количество обнаруженных дефектов этого уровня.

Минимальные границы:

| Фаза | Низкая | Средняя | Высокая | Критическая |
|---|---:|---:|---:|---:|
| Начальная | 10 % | 40 % | 50 % | 80 % |
| Основная | 15 % | 50 % | 75 % | 90 % |
| Финальная | 20 % | 60 % | 100 % | 100 % |

### 11.3 Текущее устранение дефектов

Та же формула, где `D^Level_Closed` — количество дефектов уровня `Level`, устранённых в текущем билде, а `D^Level_Found` — количество дефектов этого уровня, обнаруженных в предыдущем билде.

| Фаза | Низкая | Средняя | Высокая | Критическая |
|---|---:|---:|---:|---:|
| Начальная | 60 % | 60 % | 60 % | 60 % |
| Основная | 65 % | 70 % | 85 % | 90 % |
| Финальная | 70 % | 80 % | 95 % | 100 % |

### 11.4 Стоп-фактор

$$S = \begin{cases} Yes, & TE \ge 25\% \text{ и } TSP < 50\% \\ No, & TE < 25\% \text{ или } TSP \ge 50\% \end{cases}$$

где `S` — решение о приостановке тестирования; `TE` и `TSP` — текущие значения соответствующих метрик.

### 11.5 Выполнение тест-кейсов

$$TE = \frac{T_{Executed}}{T_{Planned}} \cdot 100\%$$

где `TE` — процентный показатель выполнения тест-кейсов; `T_Executed` — количество выполненных тест-кейсов; `T_Planned` — количество тест-кейсов, запланированных к выполнению.

Уровни: минимальный — 80 %, желаемый — 95–100 %.

### 11.6 Покрытие требований тест-кейсами

$$RC = \frac{R_{Covered}}{R_{Total}} \cdot 100\%$$

где `RC` — процентный показатель покрытия требований тест-кейсами; `R_Covered` — количество требований, покрытых хотя бы одним тест-кейсом; `R_Total` — общее количество требований.

Минимальные границы: начальная фаза — 40 %, основная — 60 %, финальная — 80 % (рекомендуется 90 % и более).

### 11.7 Покрытие кода автотестами

Доля строк, выполненных автотестами, от всех строк кода (без миграций, конфигурации и сгенерированного кода). Целевое значение — не менее 70 % (задание 2 ВПО).
