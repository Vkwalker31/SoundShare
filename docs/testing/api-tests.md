## 2. Что проверяется в каждом запросе

- **Позитивные**: код ответа, структура тела (`id`, `accessToken`, `items`, `nextCursor`), значения (роль из claims, рейтинг после голоса, порядок очереди), заголовки (`Location`, `ETag`, `Set-Cookie`, `X-Correlation-Id`).
- **Негативные**: без токена (401), чужая роль (403), чужая приватная комната (404), некорректные данные (400 ProblemDetails с полем ошибки), бизнес-правила (409), несуществующий эндпоинт (404). Для каждой ошибки проверяется формат `application/problem+json` и отсутствие стека и деталей реализации.
- **Связывание**: токен из ответа входа сохраняется в `tok_<пользователь>` и подставляется в заголовок `Authorization`; refresh-cookie — в `rt_<пользователь>`; идентификаторы пользователей, комнат и позиций очереди — в переменные коллекции.

## 3. Запуск с отчётом

Перед запуском — свежие демо-данные (`db/reset.sql`, `db/apply_migrations.sql`, `db/seed/demo.sql`) и запущенный API на `http://127.0.0.1:5290` с `RateLimiting__LoginPermitLimit=1000` (коллекция выполняет десятки входов за минуту).

```bash
npm install -g newman newman-reporter-htmlextra
newman run tests/postman/SoundShare.postman_collection.json -e tests/postman/local.postman_environment.json -r cli,htmlextra,junit --reporter-htmlextra-export docs/testing/evidence/newman-report.html --reporter-junit-export docs/testing/evidence/newman-junit.xml
```

Cookie-jar Newman отключён на всех запросах (`disableCookies`), cookie `rt` передаётся явно: иначе Newman подставлял бы последнюю полученную cookie и повторное использование отозванного токена не проверялось бы.
