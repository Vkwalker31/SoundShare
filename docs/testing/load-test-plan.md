# План нагрузочного тестирования (задание 5)

## 1. Цели

| Цель | Требование | Критерий успеха |
|---|---|---|
| Подтвердить время ответа при целевой нагрузке | NFR-PERF-01 | p95 ≤ 200 мс при 100 RPS, доля ошибок < 1 % |
| Проверить конкурентное голосование | NFR-TX, BR-VOTE-02 | Нет взаимоблокировок и потерянных голосов, ошибки 409/500 < 1 % |
| Найти точку деградации | — | RPS, при котором p95 > 500 мс или ошибок > 5 % |
| Проверить восстановление | NFR-REL | После снятия нагрузки время ответа возвращается к базовому |

## 2. Инструмент

**NBomber** (C#, проект `tests/SoundShare.LoadTests`): сценарии на том же языке, что и приложение; HTML/Markdown/CSV-отчёты с перцентилями; модель «открытой» нагрузки `Inject` (заданное число запросов в секунду независимо от времени ответа).

## 3. Профиль нагрузки

Данные готовит сам тест через API: 60 пользователей, одна публичная комната, в очереди 11 треков.

| Сценарий | Действие | Доля | Пауза |
|---|---|---:|---|
| `read_queue` | `GET /api/rooms/{id}/queue` — обновление очереди клиентом | 70 % | Нет (открытая модель) |
| `vote` | `PUT …/items/{id}/vote` случайным пользователем за случайный трек, ±1 | 20 % | Нет |
| `list_rooms` | `GET /api/rooms` | 10 % | Нет |

## 4. Виды тестов

| Вид | Нагрузка | Длительность | Команда |
|---|---|---|---|
| Базовый | 1 виртуальный пользователь, только `read_queue` | 30 с | `dotnet run -c Release --project tests/SoundShare.LoadTests -- baseline` |
| Нагрузочный | 100 RPS: 70 + 20 + 10 | 60 с (+5 с прогрев) | `… -- load` |
| Стрессовый | Ступени по 30 с: 100, 200, 400, 600, 800, 1000 RPS | 180 с | `… -- stress` |

## 5. Окружение

Одна машина: API (Release, Kestrel) и Oracle 23ai Free в Docker; генератор нагрузки на той же машине, поэтому результаты — нижняя оценка. Перед каждым прогоном демо-данные пересоздаются, фоновые службы включены. Ограничитель частоты входа поднят (`RateLimiting__LoginPermitLimit`), так как подготовка данных выполняет 60 входов.

## 6. Метрики

RPS, доля ошибок, время ответа (min, mean, p50, p75, p95, p99, max) по сценариям, коды ответов. Параллельно фиксируются `EXPLAIN PLAN` запросов очереди (этап 7 МДиСУБД) и время `GET /api/rooms/{id}/queue` в журнале аудита.
